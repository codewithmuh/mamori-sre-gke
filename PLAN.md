# Plan: an SRE platform on GKE, run under user-journey SLOs, with an AI incident agent

Status: **repo created 2026-11-13; issues open; M0 in progress.** Decisions were answered on 2026-11-13 (Rashid's
answers are in section 8); M1 starts Sat 2026-11-14. Each decision becomes an ADR that Rashid writes from scratch in
M0, with no AI draft. Progress is tracked in the
[milestones](https://github.com/codewithmuh/mamori-sre-gke/milestones) and
[issues](https://github.com/codewithmuh/mamori-sre-gke/issues).

## 1. What this project has to prove

Production SRE work on Google Cloud means running a fleet of microservices on GKE under SLOs built around critical
user journeys (CUJs), leading incidents and postmortems, designing alerts that don't cause alert fatigue, writing
Terraform and Go, and building AI agents that detect, triage and recover from incidents under safety guardrails.
This project has to show each of those.

**The lesson from secure-file-transfer:** that project has eight SLOs, burn-rate alerts, runbooks and DR drills,
all designed and statically tested, but none of it has run (its own docs say "pending the AWS run"). In SRE work,
*operated* evidence counts for more than *designed* evidence. So this project is judged by one rule:

> **It is done when it has run for weeks and the numbers in the case study are measured, not when the code is
> complete.**

That means small product scope, cheap to keep running, steady (synthetic) traffic all the time, and failures
injected on purpose so there are real incidents to respond to.

## 2. Scope

**In scope**

- One GKE cluster in Tokyo (asia-northeast1), Terraform for everything, GitOps with Argo CD.
- A fleet of 10 application microservices (plus a load generator) that the SRE did not write (section 3, D1), with Istio in front for traffic control and
  fault injection.
- CUJ SLOs for 3–4 journeys, found by fault injection (section 4), generated as code, with burn-rate alerts and an
  error-budget policy.
- The shop's frontend public at a subdomain of codewithmuh.com behind a rate-limited load balancer, so outside probes
  and synthetics test it the way users reach it (D11).
- A spend guard: budget alerts, and at 100 % the node pool scales to zero (D12).
- An on-call setup that pages a phone, an incident process, game days, postmortems.
- An AI incident agent with guardrails and a measured evaluation.
- Capacity, autoscaling, load shedding and dependency hardening, each with before/after numbers.
- Production readiness and compliance as code.

**Out of scope (on purpose)**

- Writing a product. The SRE's job is to run services others wrote; product features add weeks and prove nothing
  about operations.
- Multi-region and DR. secure-file-transfer already covers that design; here it would double the cost.
- Spanner or AlloyDB. Too expensive for a lab; Cloud SQL or Memorystore only if a decision needs one.
- A 10K QPS claim. The capacity test reports whatever the cluster actually holds, and the cost to scale it.

## 4. Architecture sketch

```
GitHub (monorepo: infra/, deploy/, services/ fork, tools/ in Go, agent/)
  │  PR → plan comment ─ manual apply (lab env)        images → Artifact Registry
  ▼                                                     │
GCP project (asia-northeast1)                           ▼
  VPC ─ GKE Standard (zonal, Spot pool) ◀──── Argo CD (app-of-apps)
          │
          ├─ Istio ── Online Boutique (11 services, gRPC) + Redis
          │           ▲ load: Locust (steady) · CUJ prober in Go (every minute)
          │           ▲ faults: Istio aborts/delays · Chaos Mesh · Spot preemption
          │           ▲ users: mamori.codewithmuh.com ─ load balancer + Cloud Armor rate limits
          │
          ├─ OTel Collector ─▶ Managed Prometheus · Cloud Trace · Cloud Logging
          │                     └▶ Cloud Monitoring SLOs + burn-rate alerts ─┐
          ├─ Datadog Agent (14-day window) ─▶ Datadog SLOs, monitors, synth ─┤
          │                                                                  ▼
          ├─ Gatekeeper (readiness policies) ─▶ weekly evidence bundle   PagerDuty ─▶ phone
          │                                                                  │
          └─ AI incident agent (Python) ◀── alert webhook ───────────────────┘
               │ read-only tools: PromQL, Logging, Trace, kubectl get/describe/logs,
               │ Argo CD history, Istio config, past postmortems
               │ model: Claude on Vertex AI (Workload Identity)
               ▼
             Slack: impact summary, ranked RCA, proposed action ─▶ human approves
               ▼
             Executor (Go, narrow RBAC): rollback · scale within bounds · restart ·
             remove a fault rule. One action per incident, audit-logged, kill switch.
```

### CUJ SLOs by fault injection (the core of M2)

1. **Journeys:** browse (home and product page), add to cart, checkout. Maybe view cart as a fourth.
2. **E2E tests** drive each journey through the frontend (Playwright).
3. **Discovery run:** Istio aborts one upstream gRPC service at a time while the tests run. If the journey fails, that
   service's API is *critical* to it. The output is a generated `cuj-map.yaml`.
4. **Generator (Go CLI):** reads `cuj-map.yaml` and writes the recording rules, Cloud Monitoring SLOs, Datadog SLOs
   and monitors, and dashboards as Terraform and YAML. Availability per CUJ = product of the critical APIs' success
   rates; latency = the lowest achievement rate among them. How to express the product in each backend is a design task
   in M2.
5. **Re-run in CI** on every change to the services, so the map never goes stale (the reason the published method was
   built). A dependency that should not be critical but is (say a currency-service outage takes down every page, when prices could fall back to USD) becomes a
   hardening task in M4.

### The incident agent (M5): extends `ai-sre-investigator`

That repo already has a Claude tool-use loop with read-only PromQL, LogQL, kubectl and recent-deploy tools, a CLI,
an Alertmanager webhook and a human approval gate, running on kind. M5 moves it to GKE and adds:

- **Detection:** burn-rate alerts trigger it (Cloud Monitoring, Alertmanager and Datadog webhooks).
- **Triage:** which CUJ is burning, a user-impact statement, a proposed severity.
- **RCA:** GCP tools (Managed Prometheus API, Cloud Logging, Cloud Trace), Argo CD history, Istio config, and search
  over our own past postmortems ("has this happened before?").
- **Recovery:** the executor (D9). It starts human-in-the-loop for every action. Low-risk actions move to
  human-on-the-loop later: they run automatically, notify, and revert if the SLO doesn't recover in N minutes.
- **Evaluation:** a fault library of 20–30 incidents with known root causes, from the game days. Measured: detection
  time, top-1 and top-3 RCA accuracy, correct-action rate, unsafe actions attempted and blocked, cost and time per
  investigation. Baseline: the human time to root cause in the M3 game days.

## 7. Risks

| Risk | Mitigation |
|---|---|
| **The secure-file-transfer pattern: built, never run** | Run from M1. The definition of done is measured numbers. Small product scope (D1). |
| **Too many projects in flight** (secure-file-transfer still waits for its AWS run) | Other portfolio projects paused while this runs (Rashid's call). Reuse secure-file-transfer's SLO, runbook and drill formats instead of writing new ones. |
| Credit runs out or bill surprises | Budget alerts at 50/90/100 % and the scale-to-zero guard (D12); `make down` with a leftover check; Spot only; upgrade to paid at M5 so a spent credit can't stop the cluster mid-plan |
| A trial account can't raise quotas | Check the region's CPU quota in M1; size node surge upgrades to fit; run the M4 capacity test after the upgrade, when increases can be requested |
| A public shop with a card form on a codewithmuh.com subdomain looks like phishing (Safe Browsing could flag the domain) or someone types a real card | "Demo shop, no real payments" banner on every page; the checkout keeps the demo's pre-filled fake card; no real accounts; Cloud Armor rate limits |
| PagerDuty's free plan allows 100 phone/SMS pages a month | Count pages; a noisy alert that uses up the allowance is an alert-fatigue finding (R5); push notifications are unlimited |
| Datadog's 14 days are wasted | Account created only when the Terraform is ready and the game days are scheduled |
| "Online Boutique is a tutorial" | The app is the given; the work is the SRE layer. The README says so in the first paragraph. |
| Lab numbers look like production claims | Every number in the case study states it is from a lab with synthetic load. Wherever the project is described, it is a lab project, never "production". |
| Agent does something unsafe | D9: RBAC limits, allow-list, one action per incident, approval, audit log, kill switch, and evaluation before any automatic action |
